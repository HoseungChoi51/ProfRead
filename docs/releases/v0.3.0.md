# AfterDraft v0.3.0 — From discussion to deliberate revision

Released: 2026-08-11

AfterDraft v0.3.0 closes the loop between reading, discussion, and revision.
Useful conversational AI answers now become editable annotation candidates by
default. A new
document-level Writer can use only the discussions, saved annotations,
highlights, and artifacts the reader explicitly selects, then propose
reviewable block edits without changing the article on its own. Stale summaries
can be reviewed semantically: the model keeps an already-sufficient summary or
provides a complete replacement only when the current article or reader signals
contain a material gap.

This is a forward-only database release. Back up the complete persistent volume
before upgrading.

## What is new in v0.3.0

### Automatic annotation candidates

- A completed Define, Explain, ELI14, Ask, Research, or Visualize answer in a
  passage-anchored discussion creates a pending, readable annotation candidate
  automatically. Structured summary and recap artifacts are intentionally
  excluded.
- Candidates prefer the first two useful sentences, normalize common Markdown,
  and are bounded to 500 Unicode code points. This makes concise Define results
  immediately useful while giving longer explanations a practical starting
  point.
- The candidate appears in the existing thread annotation editor. The reader
  can revise it, use the lightweight **Polish with AI** action, save it, or
  dismiss it.
- A newer answer can refresh a still-unsaved candidate. An explicitly saved
  annotation is never overwritten by later model output.
- Candidates and their source answer are persisted separately from the original
  discussion. Only an annotation the reader explicitly saves is treated as
  curated knowledge or included in exports.

### Document Writer

- Every article can have one persistent, document-level **Writer** session,
  separate from passage discussions.
- Add individual assistant answers, saved thread annotations, semantic
  highlights, or artifacts to the Writer source basket. Cross-document sources
  are rejected.
- Sources are snapshotted when selected. Later edits to the original discussion,
  highlight, annotation, or artifact cannot silently change what an existing
  proposal was grounded in.
- Writer requests receive the complete effective article as an ordered,
  block-indexed document, the persistent Writer conversation, the latest prior
  proposal, and only the explicitly selected source snapshots.
- A capable configured model is forced to call the structured
  `propose_document_edits` tool exactly once. Freeform prose cannot bypass the
  proposal validator.
- Proposals contain a title, summary, and up to 200 individually reviewable
  changes. Every change shows its current text, proposed operation, rationale,
  and selected source references.
- The reader chooses which changes to apply. Unselected changes remain
  unapplied; the Writer never writes the article autonomously.
- Supported Writer changes are safe text replacement, insertion of a text block
  before or after an existing block, and deletion of a text block. Inserted text
  is escaped as text rather than interpreted as HTML.
- The primary article heading, media, tables, scripts, styles, and unsafe nested
  insertion boundaries are protected from destructive Writer operations.
- A proposal is applicable only while its document version, edit revision,
  effective HTML hash, and Writer source-set hash still match the generation
  snapshot. Stale proposals must be regenerated.
- Applying a selected proposal creates a normal immutable article edit revision
  with `writer-proposal` provenance. Manual edits, restores, sanitizer refreshes,
  and Writer applies share a server-side per-version mutex and recheck the base
  revision inside the lock.
- Proposal application is idempotently guarded by its origin ID, so a retry
  cannot apply the same proposal twice.

### Semantic summary review

- A document TL;DR, half-page summary, or visual recap marked **Needs review**
  or **Unknown** now offers **Review changes** in addition to **Regenerate** and
  **Keep current**.
- Review is a user-triggered structured model request against the complete
  effective article, the existing artifact, deterministic stale reasons, and
  the exact current Important and Reader Comment signals.
- The review classifies article-level fidelity as adequate, a material gap, or a
  contradiction and returns exactly one coverage judgment for every supplied
  reader signal.
- **KEEP** is valid only when the article-level review is adequate and every
  signal is materially covered. Different wording is accepted; a revision or
  signal-hash change alone is not a reason to regenerate.
- **REPLACE** is valid only for a source gap, contradiction, or uncovered
  signal, and must include the complete kind-valid replacement in the same
  structured response.
- TL;DR replacements are validated at no more than five bullets and 150 words
  or CJK characters. Half-page replacements must contain 300–450 words or CJK
  characters. Visual recap replacements must satisfy the versioned recap
  schema.
- A visual recap KEEP reuses the existing image and makes no image-generation
  request. A visual REPLACE generates a candidate PNG and exposes it only if the
  review can still be committed.
- Review captures the artifact version, document version, edit revision,
  reader-signal hash and snapshots, existing content, source references, and
  article hash before invoking a provider.
- Final application uses artifact-version and exact-basis compare-and-swap in a
  single database transaction. If the article, signals, or artifact changes
  while review is running, the verdict is recorded as superseded and applies
  nothing.
- Applied, superseded, failed, and cancelled reviews remain auditable and are
  replayed for an identical completed request ID without another provider call.
- The artifact UI exposes the latest decision, rationale, model, time, and
  applied basis. Manual **Keep current** remains available and now also requires
  the expected artifact version.

### Safer structured model execution

- `document-write` and `review-summary` have explicit model routes, capability
  requirements, prompt components, and per-request model overrides.
- Both native Responses and compatible Chat Completions providers can forward
  arbitrary internal function tools and force one named tool choice.
- Writer requires text, streaming, structured output, and function-tool
  capability. Summary review has the same requirements; visual recap review
  additionally requires Responses image generation.
- Full-context token estimates are checked before provider invocation. A model
  that cannot fit the complete Writer or review input is rejected rather than
  silently receiving a truncated article.
- Singleton summary generation now increments artifact versions and uses the
  version observed at request start, preventing a slower concurrent generation
  from overwriting a newer result.

## Existing capabilities retained

v0.3.0 retains the complete v0.2 reader and editing workflow:

- safe HTML and HTML-plus-assets ZIP import, immutable source versions, article
  groups, search, deletion confirmation, and reading-progress restoration;
- sanitized CSP-restricted reading with bundled styles and supported images,
  SVG, tables, figures, and video;
- collision-aware selection actions, Copy, semantic highlights, Define,
  Explain, ELI14, Ask, Compact, TL;DR, half-page, visual recap, visualization,
  and Research;
- a reserved bottom Ask composer, exact selection reveal, keyboard submission
  and cancellation, retry-safe request IDs, model override, and streamed Stop;
- durable discussions, nested answer questions, Markdown responses, concise
  saved annotations, automatic two-line article previews, and answer Copy;
- Important, Question, and Comment highlights with notes, accessible patterns,
  exact repeated-range anchoring, editing, deletion, and repair;
- desktop editing beside the discussion pane, Save & Ask, revision history,
  restore, inline formatting, folded sections, media captions, and image resize;
- revision-aware summary freshness, reader-signal-aware generation prompts,
  artifact pinning, source references, citations, tool events, route and usage
  metadata;
- self-contained annotated HTML, Markdown notebook, and printable PDF export,
  with optional full discussion history; and
- single-owner authentication, CSRF protection, server-held provider secrets,
  configurable models/routes/prompts/context, backup/restore tooling, health
  checks, and the convenience restart script.

## Database migration and compatibility

Migration 12 runs automatically after migration 11 and is forward-only. It:

- distinguishes ordinary discussion threads from the one Writer thread allowed
  per document;
- adds pending/accepted/dismissed annotation-candidate fields and the source
  assistant-message reference;
- adds immutable `writer_sources` and revision-bound `writer_proposals` tables,
  with uniqueness guards for one Writer, one active draft, and one active Writer
  run per thread;
- adds `origin_type` and `origin_id` to edit revisions, with a unique origin
  guard for idempotent Writer application; and
- adds `summary_reviews`, including artifact-version and basis snapshots,
  structured result/audit data, and terminal applied, superseded, failed, or
  cancelled state.

Existing documents, imports, anchors, discussions, messages, annotations,
highlights, artifacts, edit revisions, exports, sessions, settings, prompt
overrides, and model-run history remain in place. The migration is guarded so a
partially upgraded development database can restart safely.

To roll back, restore a pre-upgrade backup. Do not point a v0.2 image at a data
volume after migration 12 has run.

## Deliberate limitations

- The Writer proposes text changes only. It does not autonomously rewrite raw
  HTML, CSS, scripts, tables, media, layout, or formatting, and it never applies
  a proposal without an explicit reader selection.
- Writer grounding is intentionally opt-in: a discussion or artifact is not
  visible to the Writer until the reader adds it to the source basket.
- Semantic summary review is user-triggered rather than a background job. The
  deterministic freshness badge remains the inexpensive first signal.
- Fresh summary generation uses explicit reader-signal-aware prompt contracts,
  but remains prompt-best-effort. Exact per-signal coverage validation happens
  when the reader runs semantic review on a stale or unknown summary.
- A review requires the complete effective article to fit an eligible model
  context window; v0.3 does not use lossy map-reduce review to manufacture a
  definitive KEEP decision.
- Automatic annotation candidates remain suggestions. Only saved annotations
  are curated knowledge and export content.
- AfterDraft remains a private single-owner workspace. Multi-user collaborative
  editing, PDF/EPUB/live-URL ingestion, vector search, arbitrary browser or
  shell tools, and general-purpose autonomous agents remain outside this
  release.
